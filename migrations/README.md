# `migrations/` — control-plane schema

This directory is the Alembic environment for the local PostgreSQL control plane defined in
[`src/lance_etl/state/tables.py`](../src/lance_etl/state/tables.py). It contains exactly one
revision. There is no migration chain, no compatibility bridge for an older experimental schema,
and breaking changes to the schema are expected and allowed — see the "Migration strategy" section
of [ADR 0042](../docs/adr/postgresql-dataset-control-plane.md).

For the 9-table entity model this migration creates, see
[`src/lance_etl/state/README.md`](../src/lance_etl/state/README.md) and ADR 0042. For the
reconciler process that runs this migration, see
[`src/lance_etl/reconciler/README.md`](../src/lance_etl/reconciler/README.md). For the hard coding
rules that govern this directory, see the repository-root [`AGENTS.md`](../AGENTS.md) (rule 1: no
inline comments or leading underscores here either, docstrings only).

## Layout

| File | Responsibility |
|---|---|
| `env.py` | Alembic runtime environment: wires `target_metadata` to `lance_etl.state.tables.metadata` and runs migrations online (live psycopg connection) or offline (SQL emission without a connection) |
| `versions/0001_control_plane.py` | The single baseline revision: creates all 9 tables and their constraints and indexes, seeds the bundled default specification, and installs the lifecycle-enforcement triggers |
| `../alembic.ini` | Alembic configuration at the repository root: `script_location = migrations` and a default local `sqlalchemy.url` |

## A single-revision baseline

`versions/0001_control_plane.py` declares `revision = "0001_control_plane"` and
`down_revision = None` — it is both the first and, currently, the only revision. `upgrade()` runs in
a fixed order:

1. `create_settings_and_spec_tables` — `dataset_spec_revisions`.
2. `create_field_and_index_tables` — `dataset_fields`, `index_definitions`.
3. `create_source_and_dataset_tables` — `iceberg_sources`, `datasets`, `source_snapshots`.
4. `create_work_and_publication_tables` — `dataset_work`, `dataset_publications`,
   `publication_indexes`.
5. `seed_defaults` — inserts the bundled default specification.
6. `create_lifecycle_triggers` — installs the PostgreSQL functions and triggers described below.

`downgrade()` drops every table in reverse dependency order and drops the trigger functions. Because
there is only one revision, `downgrade()` is effectively "drop the entire control plane" rather than
a step back to an earlier schema.

Each `op.create_table` call in this file re-declares its columns, `CheckConstraint`s,
`UniqueConstraint`s, and `ForeignKeyConstraint`s inline, mirroring `state/tables.py` by hand rather
than importing its `sa.Table` objects. This is deliberate Alembic practice: a migration is a
historical, immutable record of the schema at one point in time, while `tables.py` is live metadata
that may keep evolving. Today, with a single revision, the two must be kept in sync by hand whenever
either changes — a future second revision would instead express only the *diff* against this
baseline.

## How `env.py` wires autogenerate

`env.py` sets `target_metadata = lance_etl.state.tables.metadata` — the same `MetaData` object that
defines every `sa.Table` in `state/tables.py`. This is what makes `alembic revision --autogenerate`
possible: Alembic diffs the live database against `target_metadata` and proposes a new revision
script for the difference. `run_migrations_online()` builds a connection from the `[alembic]`
section of `alembic.ini` (or an override, see below) via `engine_from_config` with `NullPool`, since
a one-shot migration run has no reason to hold a connection pool open.

Because `0001_control_plane.py` was handwritten rather than autogenerated (it needed the seed data
and the trigger installation, which autogenerate cannot produce), the current single revision is not
itself a worked example of an autogenerate diff — but the wiring is in place for the first genuine
second revision to be drafted that way and then hand-edited for anything autogenerate cannot express
(seed rows, triggers, data backfills).

## Trigger-based lifecycle enforcement

`create_lifecycle_triggers` installs five PostgreSQL objects that enforce the DRAFT -> ACTIVE ->
RETIRED specification lifecycle at the database layer, independent of and in addition to the checks
`ControlPlaneRepository` performs in Python (see
[`state/README.md`](../src/lance_etl/state/README.md#specification-lifecycle-draft---active---retired)):

- **`require_draft_spec_revision(candidate_revision_id)`** — a helper function that raises
  `ERRCODE 23514` (`ck_specification_children_draft`) unless the given revision is currently DRAFT.
- **`enforce_spec_revision_lifecycle()`**, triggered `BEFORE INSERT OR UPDATE OR DELETE ON
  dataset_spec_revisions` — a new row must be inserted as DRAFT, and DELETE is only permitted while
  DRAFT. A DRAFT row may transition to DRAFT (no-op) or to ACTIVE (and only if every column except
  `state`/`activated_at` is unchanged from the stored row, checked via `to_jsonb` diffing). An
  ACTIVE row may transition to RETIRED under the same unchanged-columns rule. Every other UPDATE is
  rejected. This is what makes ACTIVE and RETIRED rows immutable at the SQL layer.
- **`enforce_direct_spec_child_lifecycle()`**, triggered on both `dataset_fields` and
  `index_definitions` `BEFORE INSERT OR UPDATE OR DELETE` — calls `require_draft_spec_revision`
  against the row's (old and/or new) `spec_revision_id`, so a field or index definition can only be
  inserted, changed, or removed while its owning revision is DRAFT.
- **`enforce_active_dataset_revision()`**, triggered `BEFORE INSERT OR UPDATE OF
  desired_spec_revision_id ON datasets` — requires the referenced revision to currently be ACTIVE,
  matching the repository's `assign_dataset_spec_revision` precondition.
- **`enforce_source_default_active()`** — installed as a `DEFERRABLE INITIALLY DEFERRED CONSTRAINT
  TRIGGER` on both `iceberg_sources` (`AFTER INSERT OR UPDATE OF default_spec_id`) and
  `dataset_spec_revisions` (`AFTER INSERT OR UPDATE OR DELETE`). Being deferred means it is checked
  once at transaction commit rather than after each statement, so a single transaction can retire
  the old ACTIVE revision and promote a new one (`activate_spec_revision`'s two-statement sequence)
  without tripping the constraint mid-transaction. At commit it scans every source and rejects the
  transaction if any source's `default_spec_id` no longer resolves to an ACTIVE revision.

## Running migrations

### `lance-etl-reconcile migrate`

`AlembicMigrationRunner` (`src/lance_etl/reconciler/migrations.py`) is the supported way to run
migrations. It reads `LANCE_ETL_DATABASE_URL` through `control_plane_database_url()` (which
validates the psycopg 3 driver and requires `sslmode=verify-full` plus an absolute `sslrootcert` for
any non-local host), resolves the repository root from the installed package location, and
programmatically sets `script_location` and `sqlalchemy.url` before calling
`command.upgrade(configuration, "head")`. It works from any working directory and always targets the
database named by the environment, which is why it is the command documented in the package README
and used by `bench/` and integration tests:

```bash
export LANCE_ETL_DATABASE_URL='postgresql+psycopg://lance_etl:lance_etl@localhost/lance_etl'
uv run lance-etl-reconcile migrate
```

### Raw `alembic`

Running `alembic` directly bypasses `LANCE_ETL_DATABASE_URL` entirely: `alembic.ini`'s
`sqlalchemy.url` is a literal value (`postgresql+psycopg://localhost/lance_etl` by default) with no
environment-variable substitution, and its `script_location = migrations` is a path relative to the
current working directory. Raw `alembic` therefore only works out of the box from the repository
root, and only targets the database baked into `alembic.ini` unless that file is edited:

```bash
cd /path/to/lance-etl
alembic upgrade head
alembic revision --autogenerate -m "describe the change"
```

Use raw `alembic` for authoring a new revision (`--autogenerate` needs `env.py`'s
`target_metadata` wiring) and for inspecting history (`alembic history`, `alembic current`). Use
`lance-etl-reconcile migrate` for actually upgrading a real deployment, since it is the form that
respects `LANCE_ETL_DATABASE_URL` and the remote-TLS validation.

## Invariants a maintainer must not break

- **Exactly 9 tables.** Do not add a tenth application table or a JSON/JSONB configuration blob
  column. Every new data-path option is a typed, validated column on the appropriate normalized
  entity, included in the specification digest computed by `state/specs.py`. See ADR 0042's
  "Configuration boundary" section.
- **The seed digest must match code.** `seed_defaults` inserts `DEFAULT_CONFIGURATION_DIGEST_HEX`
  (from `state/specs.py`) as the seeded revision's `configuration_digest`. Changing the bundled
  default specification's fields, indexes, or policy values in `specs.py` without regenerating that
  constant will fail `tests/test_state_postgres.py::test_migration_creates_exact_entities_and_seeded_typed_configuration`,
  which asserts the migrated database round-trips back to the same `DatasetSpecRevision` that
  `production_default_spec_revision()` builds in Python.
- **Both immutability layers stay in sync.** If a specification lifecycle rule changes in
  `ControlPlaneRepository`, the matching trigger function in `create_lifecycle_triggers` must change
  with it, and vice versa — they are meant to enforce the identical rule from two directions.
- **No raw SQL string interpolation of untrusted values.** Every dynamic fragment in this file's
  `CheckConstraint` and trigger bodies is a fixed, code-owned string (table/column names, enum
  values), never a runtime or user-supplied value. This directory is also subject to hard rule 1 (no
  inline comments, no leading underscores) and hard rule 3 (no raw SQL in application query paths —
  the DDL and trigger bodies here are schema definition, not the gRPC filter path that rule targets).

## Testing

| Test file | Covers |
|---|---|
| `tests/test_state_postgres.py::test_migration_creates_exact_entities_and_seeded_typed_configuration` | Runs the migration against a real, isolated-schema PostgreSQL database and asserts the exact table/constraint/trigger shape and the seeded default specification round-trip |

Both are real-PostgreSQL tests gated on `LANCE_ETL_TEST_DATABASE_URL`:

```bash
export LANCE_ETL_TEST_DATABASE_URL='postgresql+psycopg://lance_etl:lance_etl@localhost/lance_etl_test'
.venv/bin/pytest tests/test_state_postgres.py -k migration -m "not integration"
```
